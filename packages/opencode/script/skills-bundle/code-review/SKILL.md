# Code Review

## 리뷰 우선순위

1. **정확성** — 로직이 요구사항을 올바르게 구현하는가
2. **보안** — 입력 검증, 인증/인가, SQL 인젝션, XSS 등
3. **성능** — N+1 쿼리, 불필요한 루프, 메모리 누수
4. **가독성** — 변수명, 함수 크기, 주석의 적절성
5. **테스트** — 핵심 로직에 대한 테스트 존재 여부

## 체크리스트

### 보안
- [ ] 사용자 입력이 검증/이스케이프 처리됨
- [ ] 민감 정보(비밀번호, 토큰)가 로그에 출력되지 않음
- [ ] SQL 파라미터 바인딩 사용 (raw string 금지)
- [ ] 적절한 인증/인가 검사

### 에러 처리
- [ ] 예외가 적절히 catch되고 사용자에게 안전한 메시지 반환
- [ ] 에러 로그에 충분한 컨텍스트 포함
- [ ] null / undefined 처리

### 코드 품질
- [ ] 함수가 단일 책임을 가짐 (20줄 초과 시 분리 검토)
- [ ] 매직 넘버/문자열 대신 상수 사용
- [ ] 중복 코드 없음 (DRY)
- [ ] 불필요한 주석 없음 (코드가 이미 설명적이면 주석 불필요)

### 테스트
- [ ] 새 기능에 단위 테스트 포함
- [ ] 엣지 케이스 (빈 값, 최댓값, 경계값) 테스트
- [ ] 기존 테스트 모두 통과

## 피드백 작성 기준

| 레벨 | 표시 | 의미 |
|---|---|---|
| 필수 수정 | `[blocker]` | 머지 전 반드시 수정 |
| 제안 | `[nit]` | 작은 개선 사항, 선택적 |
| 질문 | `[question]` | 의도 확인 필요 |
| 칭찬 | `[nice]` | 잘 작성된 부분 |

### 피드백 예시

```
[blocker] 이 SQL 쿼리는 사용자 입력을 직접 문자열에 포함하고 있어 SQL 인젝션에 취약합니다.
파라미터 바인딩으로 수정해 주세요.

[nit] `getUserList` 대신 `getUsers`가 더 간결합니다.

[question] 여기서 트랜잭션을 사용하지 않는 이유가 있나요?
두 쿼리 사이에 실패하면 데이터 정합성 문제가 생길 수 있습니다.
```

## 리뷰 시 피해야 할 것

- 개인 취향을 "필수"처럼 표현하지 말 것
- 코드 전체를 다시 작성하라고 요구하지 말 것
- 구체적인 수정 방법 없이 "잘못됐다"고만 하지 말 것
